# CHIM agent guide

## Identify the installation

CHIM consists of a Windows Skyrim client and a separate PHP/PostgreSQL backend, HerikaServer. SKSE means Skyrim Script Extender; LLM means language model; STT and TTS mean speech-to-text and text-to-speech.

- **Installed mod:** locate the active mod-manager profile and winning files for `SKSE/Plugins/AIAgent.dll`, `AIAgent.esp`, `Scripts/` and `PrismaUI/`. Files elsewhere may be overridden or unused.
- **Source checkout:** [CHIM](https://github.com/Dwemer-Dynamics/CHIM) contains `Plugin/` and `AIAgent/`. Record `git status --short --branch` and `git rev-parse HEAD`. Historical `HerikaAI-NG` and `aiagent-aiff` trees are not the current source.
- **Server:** [HerikaServer](https://github.com/Dwemer-Dynamics/HerikaServer) owns providers, profiles, prompts, memories and database state. Read its own `AGENTS.md` before changing it.

Record the Skyrim runtime, SKSE version, CHIM client version, server version and enabled extensions. The package's `fomod/info.xml`, native startup log and server's `.version.txt`/`.version_number.txt` provide version evidence. Do not infer binary provenance solely from a folder name. Online `unstable` links describe current development, which may differ from the installed release.

## How a turn works

1. Native code and Papyrus observe the world and receive player input. PrismaUI supplies the in-game web interface.
2. The client sends game events and conversation context to HerikaServer over HTTP. Voice capture uploads use the server's STT route.
3. HerikaServer records events, selects profiles/context, calls the configured LLM and produces dialogue/actions and TTS audio.
4. CHIM receives responses, resolves the intended actor, plays speech and applies permitted game actions through native/Papyrus code.
5. Load, halt and conversation changes can invalidate work. A successful HTTP response is not proof that the correct actor spoke or completed an action.

Actor identity: events capture their audience on the game thread when they happen and add `identity_version` 2, `participants` (`{name, id?}`), `speaker_key`, `listener_keys` and `target_key` to the base64 JSON in request field 4 (`Plugin/EventIdentityUtils.h`). Keys are `player`, `narrator`, `ref:<plugin>|<local id>` or a persisted `dyn:<uuid>` for FF actors, checked against the same grammar as HerikaServer `chimIsActorKey()`; an actor without a key has no `id`, and names never become keys. A captured empty audience (private narrator lines) is still sent as version 2. Paths: player input and its `_speech` (routing snapshot), NPC `_speech` (`SpeakManager::QueueSpeechLog`, game-thread task, one snapshot per speaker, listener and response), `infonpc_close` (the listed actors) and the observable types in `IsObservableEventType()` through `HTTPManager::log`/`streamForActor` (player hearing scope; the event actor is only `target_key`). `bored` keeps fields 0-4 unchanged (`bored|ts|gamets|location|seed name`) and adds the same identity object as base64 JSON in field 5, with the seed actor as `target_key`; a `bored` request that does not have exactly five fields is dropped rather than sent. Hearing scope covers managed and unregistered loaded actors within the MCM hearing distance that `SpatialAwareness` lets hear the source; the typed narrator (`isNarrator()`) never gets a seat, and the player is a participant of NPC speech only when within the auto hearing radius or reachable by voice. Roles come from actor pointers or the server's decorated `[RefID: …]` listener only; a bare name, including one equal to the player or narrator name, stays unresolved and never becomes a role or a participant. A captured identity that is invalid, or that cannot be attached, drops the event with an `[ACTOR_IDENTITY] Dropping` warning instead of sending it as legacy; so does an off-thread event whose actor no longer resolves or whose game-thread capture is older than 30 s. Other request types (control, configuration, registration, `rechat`, `memory`) stay in the legacy format. Before field 4 is added, `|` in the data field becomes `|` in JSON data and `/` in text. `addnpc` and `addbgnpc` send the actor key as `@` field 45 (0-based, after the reference source at 44).

Action identity: `command`, `confirmcommand`, `approvedcommand` and `rolecommand` items are bound on the game thread when first queued (`SPGResponse::CaptureActionTarget`; off-thread producers post a task and keep their load generation). The binding is the actor handle, FormID and canonical key of the agent and of each existing actor a role command names (`RoleCommandActorArgs()`; base forms such as spawn templates are never treated as actors). Confirmation and approval reuse it. Before dispatch, `StillTargetsCapturedActor` requires the same load, the bound handle still naming that reference, and for FF actors the same `dyn:` key in the registry, so a stale agent entry over a recycled slot is refused with `[ACTION_IDENTITY] Dropping`. A bare name binds only when one loaded actor carries it; a decorated or malformed reference that does not resolve is refused, never matched by label. `death`, `playerdied`, `npc_reanimated` and targeted `npcspellcast` send the victim or target as `target_key` with the player hearing-scope audience. `AIAgentAIMind` reports `commandEndedForActor` as `Name [RefID: XXXXXXXX]`.

Response identity (client side of HerikaServer paired change; the server does not emit it yet): a streamed `label|queue|payload` line may carry a fourth field, standard base64 of `{"response_identity_version":1,"actor":{"id","refid"},"listener":null|{"id","refid"},"targets":[{"arg","id","refid"}]}` (`EventIdentityUtils::ParseResponseLine`). `id` is a canonical actor key; `refid` is the 8-digit uppercase runtime RefID, consistent with the key (`ref:` keeps its plugin-local id, `dyn:` is FF). The narrator is `{"id":"narrator","refid":null}` only, never RefID `00000014` (its engine object is the player); the player is `{"id":"player","refid":"00000014"}`. `arg` is the zero-based argument after the command name and only names actor arguments. With the field present the label is presentation only, including physical actors named like the narrator or player; a null listener means none and the payload's bare listener is not used. Unsupported versions or keys, malformed endpoints, conflicting targets, a fifth field or a decorated label naming another RefID drop the line (`[RESPONSE_IDENTITY] Dropping`); lines without the field keep legacy behavior. The stream's eligibility, attention and rechat target use the envelope (agent by FormID with the same profile/registry key, no key computed off the game thread). Every endpoint is bound on the game thread before queueing (a `dyn:` id must already be the slot's registry key, so a recycled slot is refused) and checked again before command dispatch and before a ScriptQueue line enters and leaves the speech queue; `ScriptLine` keeps the typed speaker/listener and bindings. Command targets must agree with their argument text, and a bare actor argument is rewritten to `Name [RefID: …]` so the branch resolves exactly; role commands bind envelope targets and refuse a named actor argument without one. Server requirement: emit the field from the selected row or typed principal on every actor-bearing output, never by name match, and keep base64 out of the slash-delimited ScriptQueue payload.

Decorated references (`ActorTargetIdentifierUtils::Parse`): only `Name [RefID: <hex>]` (terminal), `[RefID: <hex>] Name` (leading, label without brackets or another marker) and a bare `RefID: <hex>` / `[RefID: <hex>]` bind (1-8 hex digits, optional `0x`). Any other text containing `RefID:` (trailing or embedded text, unbracketed markers, bad digits) is a malformed explicit reference that names nobody; its label never selects an actor. Whether a role-command argument is numeric comes from its parameter kind (`RoleCommandActorArgs()`), never from its text, so names such as `Babe`, `Dead` or `123` are labels. Envelope targets on role commands rewrite a bare label to the bound `Name [RefID: …]`, and `ShowTrainingMenu` resolves a decorated trainer as that loaded actor only. Ordinary `command`/`confirmcommand`/`approvedcommand` actions use `OrdinaryCommandActorArgs()` instead: argument 0 of `Attack`, `Brawl`, `MoveTo`, `Inspect`, `Follow` and `TradeItems`; the JSON `target` of `GiveGoldTo`/`GiveItemTo` (argument 0 when it contains `{`, else the legacy whole argument); and `CastSpell`'s JSON `target` at argument 0 or legacy `spell@target` argument 1 (`self` and `Target Location` are not actors). With an envelope present, each non-empty actor argument must carry its target or the action is refused; the label (or JSON `target`) is rewritten to `Name [RefID: …]`, which `findActorInCell`/`resolveActionActorTarget` resolve exactly, and a target on any other argument (items, spells, locations, amounts) is refused. An envelope line with an empty fourth field but a non-empty later field is dropped (`identity_extra_field`). Off-thread response items queued while any game-thread capture is pending take the same task path, so mixed legacy and envelope lines keep their arrival order.

DirectorScene lines (client side; server does not emit it yet): each line may add `actor_identity` (`{id, refid}`, physical only) and `listener_identity` (`null` or `{id, refid}`, narrator/player allowed). With either present the line is routed by them: both are validated with the response endpoint grammar and bound on the game thread before the scene is accepted, `actor_refid` (if also sent) must be the same 8-digit RefID, the agent must have that profile key, and an invalid or unbound endpoint rejects the scene. Lines without them keep `actor_refid`/bare-speaker behavior.

ScriptProxy identity (client side; server does not emit it yet): inside the existing ScriptProxy command JSON, add `"actor_identity_version":1` and `"actor_targets":{"<parameter>":{"id":<actor key>,"refid":"XXXXXXXX"}}`, naming each actor parameter by its JSON key (for example `targetObjectFormId`, `akTarget`). Each named parameter must exist and hold that reference as a string as `jsonGetActor`/`jsonGetReference` read it (send `"0x%08X"`; unprefixed strings with a leading 0 are read as octal and numbers as nothing). When the command is queued, every top-level parameter whose value is a loaded actor reference is bound on the game thread (base forms, spells, factions, items and non-actor references are not actors); with declared metadata every such parameter must be declared and bind to its endpoint, otherwise the whole command is refused. At dispatch the bindings are checked again and passed to Papyrus as a native `chim_binding` token (stripped from any input); `jsonGetActor`/`jsonGetReference` then return only the bound actors, refuse an unbound actor, and once any binding changed refuse every getter call of that command. Unqueued local UI calls keep legacy resolution; an unqueued call carrying declared metadata is refused. Server requirement: the rolecommand line is `|`-split, so the JSON must not contain a raw `|` — canonical keys contain `|` and must be written as `\u007c` (JSON escape) inside the payload. `UploadBookContentByTitle` accepts `reader_identity` (`{id, refid}`) in its payload; without it a decorated or unique bare reader is used, and an ambiguous, malformed or unbound reader is refused rather than searched as the player. Rechat bookkeeping (chain seed, in-flight, last rechatter, deferred retry and the rechat stream's completion) is keyed by `CapturedSpeaker::RechatKey()` (canonical role `narrator`/`player`/actor key plus load generation, `ActorIdentityUtils::RechatBookkeepingKey`), never by the decorated label, so a new `dyn:` actor in a recycled FF slot is independent of the old one and a stale completion cannot clear it; `rechat()` refuses a speaker without a bound canonical key, begins the attempt itself under that key and passes it through `streamForActor` to `sendMsgStream`, which completes it once on every exit. The payload `speaker` stays the decorated presentation label. The ASAP policy rechat uses the responder and its listener captured together from the response envelope of the first line an agent answers (the speaker endpoint by RefID and key; a physical listener bound only while its RefID still holds the envelope key, read from the registry without assigning one); both are carried across the stream and rechecked in `rechat()`, never captured again at stream end, and a null or stale envelope listener stays unresolved (legacy label-only output starts no ASAP rechat). A line's speaker is captured once at dispatch (`SpeakManager::CaptureSpeaker`: type, FormID, profile key, the envelope's bound handle or the agent's current handle and registry key, and the load generation); `DownloadAndPlay` after TTS, `rechat()` and a deferred rechat retry recheck that capture (`ResolveCapturedSpeaker`), so a recycled FF slot, re-keyed agent, new load or a physical `The Narrator` or `Player` never reselects it. A rechat adds `rechat_identity_version` 1 and `speaker_key` (`narrator` or the bound actor key) next to the decorated `speaker` label, and `listener_key` while the line's envelope listener hint is still in use and still bound (a changed physical listener is sent unresolved). It also sends `active_agent_keys`, always an array (empty means nobody active): the canonical physical key each active agent entry captured on the game thread, kept only while the handle bound for that RefID still holds the same reference and, for FF actors, the same registry key; the typed narrator, keyless agents and changed actors are dropped, never replaced. `active_agents` stays the legacy bare-name list. Ordinary, ASAP and retry rechats all build the payload through `EventIdentityUtils::BuildRechatPayload`. Director scene endpoints are bound in one game-thread capture per scene (`CaptureActionTargetsFromAnyThread`). The `_speech` event for an envelope line uses the line's bound speaker/listener and their canonical keys; a changed binding sends no role, and a null listener stays unresolved with no name or player spatial fallback.

Game data identity (client side of the paired HerikaServer change): every actor-bearing `gamedata.php` row adds `actor_identity_version` 1, `actor_key` and `actor_refid` (8-digit uppercase runtime RefID) next to the display-only `actor_name` and the unchanged `actor_type` (`ActorIdentityUtils::CaptureGameDataActor`/`ApplyGameDataActorIdentity`). Rows: NPC and player `equipment`, `inventory`, `skills`, `stats`, `spells`, `activity_status` (including furniture), `transformation_state`, each element of `activity_status_bulk` `statuses` and `transformation_state_bulk` `states` (the containers carry none), `low_process_actors` (the target on the row and each `actors_nearby` entry its own), and `player_item_acquired`/`player_items_acquired` (each item and the batch). The typed player is always `player`/`00000014`, whatever its name; any other actor needs its canonical `ref:`/`dyn:` key, matched to the reference kind. The identity is captured from the same actor pointer the row is read from (`CaptureGameDataActorIdentity`): on the game thread an FF actor may be registered, elsewhere only an existing registry entry with the same base counts (`ExistingActorKey`). An unregistered FF actor is deferred (row or bulk element not sent, change hash not recorded, inventory completion fails) until a later refresh; a static reference without a canonical key (plugin not loaded, or a file name outside the key grammar such as a `.esx` extension) is never sent either, with one `[GAMEDATA_REFUSED]` warning per RefID (`HoldUnkeyedGameData`), so only old clients that send no identity reach the server's legacy compatibility. `activity_status` rows always carry `attack_target_key` and `attack_target_refid` for the engine combat target (`ApplyGameDataAttackTarget`): both set for a keyed target, both null when there is none or it cannot be keyed, and the display-only `attack_target` appears only beside a key. `scanActorsAroundOffline` captures only the target handle, FormID, existing key and load on the Papyrus thread; the process lists are walked and identities assigned in an SKSE game-thread task that drops a stale load, reused handle, changed key or deleted target. Change hashes stay keyed by FormID but are prefixed with the captured key, RefID and load generation (`GameDataChangeHash`; the player uses `player|00000014|<load>`, a hash prefix only, the player rows are unchanged), so a new `dyn:` actor in a recycled FF slot, a static `ref:` NPC or the player in a new load uploads again, and an acknowledgement only confirms the identity and load it was sent for. `GameDataDeliveryCache` records a hash only after an HTTP 2xx for the newest request of an otherwise idle lane (one lane per FormID and canonical prefix; a non-canonical or missing prefix shares one unscoped lane); overlapping or deferred sends leave it undelivered, and the 15 s stats cadence resends current equipment/inventory state through `NeedsRetry` with failure backoff of 15, 30, 60 and at most 120 s. A request with no callback after 60 s is treated as lost by `NeedsRetry` itself (counted as a failure), its lane is abandoned and its late callback is ignored. The POST itself has no hard deadline (blocking connect, 5 s socket send/receive per call, thread-pool queueing), so 60 s is a recovery window, not a guarantee that the request stopped; the server must tolerate a late duplicate of an older row and apply rows idempotently. Item, spell, quest and `form_id` fields stay base-form metadata. `quest_event` payloads (including `actor_dead`), quest acks/polls, `loaded_plugins` and the Papyrus `PostGameData` native (only `market_stock`, which names no actor) are unchanged.

Physical diary identity (client side; server does not emit it yet): `spawnBook` keeps its five arguments (`title|type|recipient FormID|taskid|b64:content`) for legacy title-cached notes, letters and containers. A sixth argument `b64:` + base64 JSON `{"identity_version":1,"book_key":"diary:<author_key>","author_key":<physical key>,"recipient_key":<physical key>}` (exactly these four fields; never `player` or `narrator`) makes it an identified diary: the recipient (argument 3) must currently have `recipient_key`, otherwise the line is dropped. The client creates the copy through the engine (`PlaceObjectAtMe` of the dedicated `AIAgent.esp` `045CEF` diary, display name set on that reference, an `ExtraUniqueID` from the recipient's `GetNextUniqueID` checked against its inventory, then `PickUpObject` by the recipient) and binds the unique id the engine actually kept to an immutable instance holding the identity and its exact text. A second delivery for a `book_key` the recipient already carries refreshes that copy's text. The title cache is never read for the dedicated diary base: a dedicated diary copy without an exact instance association (a five-argument legacy diary, or a save whose `AIBK` record is missing) shows the ordinary base book text and logs a warning, even when its title is unique; legacy cache files are kept and never adopted. Generic notes and letters keep their existing handling. Identified diaries never write the title cache; a copy that cannot be associated is removed if it never left the world, otherwise it stays unassociated and shows no identified text. Moves follow the copy by reading the destination's actual unique id; a dropped copy is tracked by its world reference until picked up. The `AIBK` cosave record (v2; v1 is read) stores each instance's owner, unique id, world reference, keys, content hash and text, so an older save restores its own text; a missing or malformed record leaves the save with no identified diaries. Reading or uploading an identified copy calls `book.php` with its own text plus `book_key`, `author_key`, `recipient_key`, `book_instance` (client instance number), `content_version` (16 hex digits, FNV-1a 64 of the text) and `reader_key` (the reading actor's key, `player` for player reads). `UploadBookContentByTitle` also accepts `book_key` in its payload to select among carried identified copies; a title naming two identified copies is refused. The deferred identified delivery is bound to the rolecommand's load and, when the queued item bound argument 3, to that bound handle; a reload or a released/rekeyed handle drops it, so an earlier load's book never reaches the same static NPC in a new load. Identified uploads keep the load of the read that queued them. Identified diaries render only their title and text; no book image file name is part of this protocol (`generateLetter`/`downloadFakeNote` remain separate). Server requirement: send the sixth argument only for physical author diaries, and key stored diary text by `book_key` and `content_version`, not title.

## Configuration and diagnostics

`Plugin/Conf.cpp` checks `Data/SKSE/Plugins/AIAgent.ini` first, then launcher discovery at `127.0.0.1:7135`, then the built-in fallback `127.0.0.1:8081/HerikaServer/comm.php`. An INI remains supported. Inspect the active file and logged selected route rather than assuming the fallback is in use. Do not replace user connection settings with these examples.

Inspect the actual SKSE log directory under the active Windows Documents/My Games location. Common folders include `Skyrim Special Edition/SKSE`, `Skyrim VR/SKSE`, or a customized game folder. Search for the recently written AIAgent/SKSE logs and check their timestamps; do not hard-code another person's Documents path. HerikaServer normally writes `log/chim.log` under its runtime root, with Apache/PHP and worker logs providing the other side of the request.

| Symptom | Evidence to collect first |
|---|---|
| Plugin does not load | SKSE loader log, runtime compatibility, winning DLL and dependencies |
| No server connection | Selected route from client log, launcher state, server HTTP/PHP logs |
| No transcript | Microphone/capture and upload evidence, STT response; playback errors alone do not prove an STT failure |
| Text arrives without speech | TTS generation result, audio download and playback logs |
| Wrong NPC or action | Actor/reference identity, request/response target and game-side result |
| Memory/profile problem | Matching server playthrough, relevant profile/history and worker logs |

Use the user's existing diagnostic controls where possible. Redact keys and private dialogue before publishing logs. Do not run database reset, cleanup, deployment or game launches merely to inspect an issue.

## NPC schedules

The NPC editor's Schedules tab creates, edits, cancels and deletes appointments. Select a recognised location, an in-game day number and appointment time. Daily repetition is 24 game hours; zero means one time. Destination validation requires the paired server and CHIM scripts connected to the game. Saved schedules stay pending until the game resolves a persistent arrival marker; unknown or ambiguous AI destinations remain reminders with a clarification request.

Travel starts three game hours early. Routine progress checks run hourly; the worker checks departure and arrival deadlines on each service tick using the accepted game clock. Early arrivals wait. At the deadline CHIM checks the actor's actual location and moves late actors to the validated marker. Combat/dialogue can defer execution. Visits finish after arrival, stays after their duration, and duties require an AI-reported outcome. Repetition starts only after releasing the previous activity. Overlapping travel windows are rejected; multiple recurring schedules require matching intervals.

CHIM Off blocks new schedule commands. An already installed travel package can continue until it is released. Cancellation/deletion waits for the game's release acknowledgement; Retry resends a stalled operation. Timeline changes invalidate old occurrences after release. Load the corresponding game and server saves together. Dynamic references and ambiguous same-name AI duties are rejected. A valid marker does not prove navmesh reachability: verify travel, waiting, teleport and package restoration in Skyrim before release.

The paired protocol uses `BackgroundCmd@actor@Schedule/run/token/operation/destination/issuedDays` and `util_npc_schedule` replies containing `run/token/actor/operation/result/marker`. Operations are validate, travel, check, ensure and release. The client restores only its owned travel override and link, and the server accepts only the pending operation's matching token, actor and clock epoch. Compile CHIMSchedule.psc alongside AIAgentAIMind.psc when building the client payload.
## Speech trace diagnostics

Search `AIAgent.log` for `[SPEECH_TRACE]` and an `utterance_id` from HerikaServer's `log/chim.log`. Records use the existing optional ScriptQueue ID field; older server lines without an ID still play normally but cannot be correlated end to end.

`received` means the parsed line reached the speech manager. `queued` and `dequeued` show queue admission and waiting time. Downloads have start/end markers and byte counts. `playback_started` is logged only after the audio engine accepts playback. `completed`, `interrupted`, `cancelled`, `skipped`, and `failed` report distinct outcomes. `subtitle_only_completed` means the existing audio-failure fallback displayed timed subtitles instead. `queue_removed` means the line was removed from the queue; active playback may still finish. A cancellation request alone does not prove playback stopped.

The existing speech callback is not proof of audible output. Missing stages remain unknown rather than being classified as success. Trace records contain IDs and bounded metadata, not dialogue or audio. Existing log levels and support-log collection apply.

Durations use the local monotonic clock. Do not compare its absolute value with the server's monotonic clock. No new network requests, protocol fields, settings, or game-state events are introduced.
